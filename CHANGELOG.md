# Changelog

## 0.16.0 - 2026.08.05

- 2026.08.06

  - Documentation - Configuration: `config_sample.yaml` was moved from the repository root to `docs/configs/` and renamed to `config_all_options_reference.yaml`. The name says what the file is: a reference of every option which exists, not a template to be used directly - it contains settings which exclude each other side by side (all three connectivity sub-blocks of the source, options belonging to different source engines, the `mapping` block while `workflow` is `standard`), so as it is it would contradict itself. The file got a header explaining this and how to use it, and all references in `README.md`, `docs/README.md`, `docs/config_parameters_map.md` and `MANIFEST.in` were updated - including the instruction "copy config_sample.yaml to a new file", which is replaced by copying only the relevant sections.
  - Fix - PostgreSQL Connector: The kind of an index (`PRIMARY KEY` / `UNIQUE` / `INDEX`) was taken from `information_schema.table_constraints`, whose rows are filtered by the privileges of the current user - a migration user without a privilege on a table would see its primary key as a plain index and the key would be recreated as an ordinary unique index instead of a primary key. `fetch_indexes()` now derives the kind from `pg_constraint.contype`, which the catalog reports regardless of privileges, and the `information_schema` join is gone. Verified to be equivalent on a live schema: identical labels for all 140 indexes, except the two exclusion constraints, which `information_schema.table_constraints` does not list at all and which were therefore labelled as plain indexes before - they are skipped by the constraints handling either way, so only the label changes.
  - Feature - Aggregates: Added migration of user defined aggregates. `fetch_funcproc_names()` selected only `prokind IN ('f', 'p')`, so an aggregate was never even listed - and `pg_get_functiondef()` cannot describe one either, it fails with "... is an aggregate function", because an aggregate has no body: it is described by `pg_aggregate`.
    - Aggregates are now listed as the object type `AGGREGATE` and `fetch_aggregate_code()` assembles their `CREATE AGGREGATE` statement from `pg_aggregate` - `SFUNC`, `STYPE`, `SSPACE`, `FINALFUNC` with `FINALFUNC_EXTRA` and `FINALFUNC_MODIFY`, the parallel support functions `COMBINEFUNC` / `SERIALFUNC` / `DESERIALFUNC`, `INITCOND`, the complete moving aggregate implementation (`MSFUNC`, `MINVFUNC`, `MSTYPE`, `MSSPACE`, `MFINALFUNC`, `MFINALFUNC_EXTRA`, `MFINALFUNC_MODIFY`, `MINITCOND`), `SORTOP`, `HYPOTHETICAL` and `PARALLEL`. Ordered-set and hypothetical-set aggregates are supported, `pg_get_function_identity_arguments()` already formats their `ORDER BY` separated argument list. `aggfinalmodify` / `aggmfinalmodify` are read only when the catalog has them (PostgreSQL 11+).
    - They are ordered **last** among the functions and procedures, because an aggregate references its state transition and final functions, which have to exist first.
    - The aggregate query runs with `search_path` set to `pg_catalog`, so `format_type()` and `pg_get_function_identity_arguments()` qualify every user defined type and support function with its schema while leaving the built-in ones bare - the existing schema replacement of `convert_funcproc_code()` then maps them to the target schema.
    - Routines belonging to an extension are excluded from the funcprocs migration (`pg_depend` with `deptype = 'e'`). Without it, including aggregates would newly try to recreate the aggregates of an extension installed into the migrated schema (`intarray`, `tablefunc`, ...).
  - Fix - Comments: A comment of a function, procedure or aggregate was read from the source and stored in the protocol table, but never set in the target - `COMMENT ON` is not part of `CREATE FUNCTION`, and the comments migration did not cover routines. The comment is now set right after the object is created, with the object type as the keyword (`COMMENT ON AGGREGATE`, `COMMENT ON PROCEDURE`, `COMMENT ON FUNCTION`) and with the identity arguments, which are required to address an overloaded routine. A comment which cannot be set is reported as a warning and does not fail the routine.
  - Fix - PostgreSQL Connector: Resolved `cannot insert a non-DEFAULT value into column "request_time" / DETAIL: Column "request_time" is a generated column.` during the data migration. Now that generated columns are really created as generated, they must not be part of the data transfer - their value is computed by the target. `migrate_table()` in `postgresql_connector.py` builds the `SELECT` and the `INSERT` from the columns without a generation expression (the same `migrated_source_columns` filter the MySQL and MariaDB connectors already use), and the fetched values are zipped against that reduced column list so the record stays aligned. Skipped columns are logged at DEBUG. A column generated only in the target (e.g. through a data type substitution) is left out as well.
  - Fix - Anonymization workflow: The data copy of the anonymization workflow built its `INSERT` from all target columns, so a table with a generated column failed the same way. Generated columns are now excluded from its `SELECT` and `INSERT` too.
  - Fix - LOB import from data files: The same problem existed in `orchestrator.lob_worker()`, used when LOB values are imported from separate data files (the Informix / DB2 UNL and CSV flow), for a table having both a LOB column and a generated column. Two things had to be corrected together:
    - The intermediate staging table was created from the DDL of the real table, so it carried the `GENERATED ALWAYS AS (...)` clauses and refused the `COPY` of the data file. The clauses are now removed by the new `postgresql_connector.strip_generated_column_clauses()`, which counts parentheses and therefore also handles an expression containing parentheses, a `CASE` expression or a string literal; `GENERATED BY DEFAULT AS IDENTITY` and `GENERATED ALWAYS AS IDENTITY` are not affected, they are not followed by a parenthesized expression.
    - `lob_col_index` is handed over as the ordinal position of the LOB column in the *full* column list and addresses the fetched row positionally. Removing a generated column in front of the LOB column shifted every following value, so the index is now re-derived from the column list actually selected - without it the LOB pointer would be read from the wrong column, or the row skipped as "Invalid lob_col_index".
  - Feature - Pre-migration analysis: Added a check of PostgreSQL extensions. Extensions are never created automatically from the source - they have to be listed in `migration.required_extensions` - and a forgotten one used to surface much later as a failing table, index or view. The analysis now reports the extensions of the source database with their version, their schema, whether they are installed in the target and whether they are at least available there, and it verifies that everything the migrated objects need is covered. A missing dependency is a blocking issue: the whole report is written and the migrator stops before anything is created.
    - The dependencies are not guessed from the SQL text. `postgresql_connector.fetch_extension_dependencies()` reads `pg_depend`, which records every type, function, operator, operator class and text search dictionary an object refers to, and attributes it to an extension through the extension membership entry (`deptype = 'e'`). Covered are the selected tables and their column types, column defaults and generated column expressions, indexes with their operator classes, constraints, triggers, views, functions / procedures and the text search objects - each finding naming the objects which need the extension (`pgcrypto: required by column documents.checksum (generated)`).
    - Only the objects the configuration actually selects are analysed - `include_tables` / `exclude_tables` are evaluated exactly as in `stdwf_prepare_tables()` (new `planner.get_tables_selected_for_migration()`), and `migrate_indexes`, `migrate_constraints`, `migrate_triggers`, `migrate_views` and `migrate_funcprocs` switch their object classes off.
    - An extension already installed in the target counts as covered, nothing has to be configured for it. When a dependency is neither installed nor configured, the report states whether it is at least available in the target ("would be installed") or not available at all ("install the operating system package providing it first"), and a ready to paste `required_extensions:` block with the complete list is logged.
    - New optional connector methods `fetch_installed_extensions()`, `fetch_available_extensions()` and `fetch_extension_dependencies()` in `database_connector.py`, returning empty results for engines without extensions.
  - Feature - Full text search: Added migration of user defined full text search objects - dictionaries (`CREATE TEXT SEARCH DICTIONARY`) and configurations (`CREATE TEXT SEARCH CONFIGURATION`) - as a new object type, created right after the collations and before the tables, because generated `tsvector` columns, views, indexes and functions reference them. This resolves `text search configuration "migtest_english" does not exist` when creating a view or a table.
    - New protocol table `<protocol>_text_search` (`migrator_tables.create_table_for_text_search()`, `insert_text_search()`, `update_text_search_status()`, `fetch_all_text_search()`, `decode_text_search_row()`, `get_migrated_text_search_objects()`) with the new config accessor `get_protocol_name_text_search()`. The objects are reported in the migration summary, dictionaries are always created before the configurations which use them.
    - New optional connector interface `fetch_text_search_objects()` / `get_create_text_search_sql()` in `database_connector.py` (returning an empty result by default - only PostgreSQL knows these objects), implemented in `postgresql_connector.py`. As with collations all non system schemas are searched, because a table of the migrated schema regularly uses a configuration created in `public`; objects belonging to an extension are left out, they come with the extension (e.g. the `unaccent` dictionary). A configuration is recreated as `PARSER = ...` plus one `ALTER ... ADD MAPPING FOR <token type> WITH <dictionaries>` per token type read from `pg_ts_config_map`, not as `COPY = <other config>` - the configuration copied from does not have to exist in the target, and the mappings were altered afterwards anyway. `COMMENT ON TEXT SEARCH CONFIGURATION` / `DICTIONARY` is transferred.
    - New planner phase `stdwf_prepare_text_search()` and orchestrator phase `run_create_text_search_objects()` (standard and anonymization workflow).
  - Fix - PostgreSQL Connector: References to text search objects were left unqualified, so they were resolved against the `search_path` of the target session, which normally does not contain the target schema of the migration. They cannot be repaired by rewriting identifiers, because they live inside a string literal (`'migtest_english'::regconfig`) - and they do not even arrive qualified: `pg_get_viewdef()` and `pg_get_expr()` print the bare name whenever the object is visible in the `search_path` of the source, so a `'public.migtest_english'` written by hand is already normalized away before the migrator reads it. The new `qualify_text_search_references()` rewrites `::regconfig` and `::regdictionary` literals of migrated objects to `'<target schema>.<name>'` and is applied to view bodies, generated column expressions, index expressions and partial index predicates, and function / procedure bodies. Built-in objects (`pg_catalog.english`) and objects owned by an extension (`ext.unaccent`) are left untouched.
  - Fix - PostgreSQL Connector: Generated columns were silently degraded to ordinary columns - `fetch_table_columns()` never read the generation expression, and it reported `is_generated_stored` as `ALWAYS` / `NEVER` from `information_schema.columns`, while `get_create_table_sql()` tests for `YES`, so the `GENERATED ALWAYS AS ... STORED` clause was never emitted and not even the existing warning appeared. The columns were created as ordinary ones and stayed permanently NULL. The generation expression is now read from `pg_attrdef` and the kind from `pg_attribute.attgenerated`, which also distinguishes `STORED` from `VIRTUAL` (PostgreSQL 18); a virtual column is created as `VIRTUAL` on a PostgreSQL 18 target and as `STORED` on an older one, with a warning. The `'+'` to `'||'` rewriting of the concatenation operator is no longer applied to a PostgreSQL source, where `'+'` really is an addition.
  - Fix - PostgreSQL Connector: Indexes lost everything their definition carries behind the key list. `INCLUDE` columns, `NULLS NOT DISTINCT`, `WITH (...)` storage parameters (such as `pages_per_range` of a BRIN index) and the `WHERE` predicate of a partial index are now taken over by the new `extract_index_tail()`; a `TABLESPACE` clause is deliberately dropped, because the tablespace of the source does not have to exist in the target. A partial index silently covering all rows was the most harmful of these.
  - Fix - PostgreSQL Connector: A plain `CREATE UNIQUE INDEX` lost its uniqueness, because `index_type` was taken from `information_schema.table_constraints`, which does not list an index that is not a constraint. `pg_index.indisunique` is used now.
  - Fix - PostgreSQL Connector: A `CREATE CONSTRAINT TRIGGER` was migrated by the constraints migration as `ALTER TABLE "..." ADD CONSTRAINT "orders_must_have_items" TRIGGER DEFERRABLE INITIALLY DEFERRED`, which is not valid PostgreSQL syntax. A constraint trigger is registered in `pg_constraint` (`contype = 't'`), but it is a trigger - there is no `ALTER TABLE ... ADD CONSTRAINT` form for it, and `pg_get_constraintdef()` returns only its deferrability, not a usable definition. `fetch_constraints()` now skips `contype = 't'`; the object is migrated by the triggers migration, which builds it from `pg_get_triggerdef()` and so keeps `CREATE CONSTRAINT TRIGGER`, `DEFERRABLE INITIALLY DEFERRED`, the `FROM` referenced table, the `WHEN` condition and the trigger comment.
  - Fix - PostgreSQL Connector: Resolved `access method "gist" does not support unique indexes` - a `UNIQUE`, `PRIMARY KEY` or `EXCLUDE` constraint is implemented by an index, and `fetch_indexes()` treated that index as an object of its own, reducing the constraint to its key list. For a temporal constraint (`UNIQUE (room, occupied WITHOUT OVERLAPS)`, PostgreSQL 18) that is not only lossy but impossible: the constraint is backed by a gist index and `CREATE UNIQUE INDEX ... USING gist` does not exist.
    - Indexes implementing a `UNIQUE` or `EXCLUDE` constraint are no longer migrated as indexes - the constraints migration creates them from `pg_get_constraintdef()`, which keeps `WITHOUT OVERLAPS`, `NULLS NOT DISTINCT`, `INCLUDE`, the `WHERE` predicate and `DEFERRABLE`. This also removes a duplicate: every unique constraint used to be created twice, once as a unique index by the index migration and once as the constraint, leaving two indexes on the target. An `EXCLUDE` constraint (`bookings_no_double_booking`) additionally used to lose its exclusion semantics and its `WHERE` clause, because the index migration created it as a plain gist index.
    - Primary keys stay with the index migration (the constraints migration deliberately skips them, so that a table gets its primary key together with its indexes), but their DDL is now built from the constraint definition instead of the index key list, so a temporal `PRIMARY KEY (product_id, valid_at WITHOUT OVERLAPS)` and a primary key with `INCLUDE` columns survive.
  - Fix - PostgreSQL Connector: Functional indexes were truncated at the first closing parenthesis, so `CREATE INDEX customers_lower_company_idx ON customers (lower(company_name))` was migrated as `CREATE INDEX ... ("lower(company_name")` - a column of that name obviously does not exist. `fetch_indexes()` extracted the index keys with the non-greedy regular expression `\((.*?)\)`, which cannot handle an expression carrying parentheses of its own. The key list is now taken with the new helper `extract_index_key_list()`, which counts the parentheses behind the access method and respects string literals and quoted identifiers, so `lower((email)::text)`, `((billing_address).city)` and `((metadata ->> 'reference'::text))` survive, and `INCLUDE (...)`, `WITH (...)` and `WHERE ...` following the key list are not taken for index keys.
  - Fix - PostgreSQL Connector: Expression indexes were not recognized as such (`is_function_based` was never set by the connector), so the expression was quoted as if it were a column name and the index was created in the standard phase instead of after the functions it may call. The flag is now taken from `pg_index.indexprs`, which states it reliably - no list of known SQL function names is needed.
  - Fix - PostgreSQL Connector: Resolved `operator class "gin_trgm_ops" does not exist for access method "btree"` when creating indexes in a PostgreSQL-to-PostgreSQL migration - every index was created as a btree, so an index like `customer_events_type_payload_idx` (`USING gin (event_type gin_trgm_ops, payload)`) failed on its operator class, and a GIN index over a `tsvector` failed with `index row size ... exceeds btree version 4 maximum ...`. `fetch_indexes()` reported the access method in `using_method` and `get_create_index_sql()` read it from its settings, but `planner.stdwf_prepare_tables()` never passed it on, so the whole `USING` handling was unreachable. The planner now passes `using_method` together with the original source index DDL (`source_index_sql`, used only as a fallback for a PostgreSQL source, because `USING BTREE` / `USING HASH` of the other engines does not name a PostgreSQL access method).
  - Feature - Collations: Added migration of user defined collations as a new object type. Collations are now discovered, planned and created as the first objects of the migration, because columns, indexes and domains reference them:
    - New protocol table `<protocol>_collations` (`migrator_tables.create_table_for_collations()`, `insert_collation()`, `update_collation_status()`, `fetch_all_collations()`, `decode_collation_row()`, `get_migrated_collations()`) with the new config accessor `get_protocol_name_collations()`. Collations are reported in the migration summary like every other object type.
    - New optional connector interface `fetch_collations()` / `get_create_collation_sql()` in `database_connector.py` (returning an empty result by default, because most source databases do not know collations as standalone objects), implemented in `postgresql_connector.py`. `fetch_collations()` reads `pg_collation` and handles the catalog differences between PostgreSQL versions (`collisdeterministic` since 12, `colliculocale` in 15/16 renamed to `colllocale` in 17, `collicurules` since 16). Because a table in the migrated schema regularly uses a collation created in another schema (typically `public`), all non system schemas are searched and collations are matched by name, the migrated schema winning on a name collision. `get_create_collation_sql()` emits `CREATE COLLATION IF NOT EXISTS` with `provider`, `locale` / `lc_collate` + `lc_ctype`, `rules` and `deterministic = false`; the recorded collation version is deliberately not copied, because the target can be built with another ICU / libc version.
    - New planner phase `stdwf_prepare_collations()` (standard and anonymization workflow) and new orchestrator phase `run_create_collations()`, which also transfers the `COMMENT ON COLLATION`.
  - Fix - PostgreSQL Connector: Resolved `collation "natural_numeric" for encoding "UTF8" does not exist` when creating indexes in a PostgreSQL-to-PostgreSQL migration. Beside the missing collations themselves, references to them were emitted unqualified (`COLLATE "natural_numeric"`) exactly as read from `pg_get_indexdef()`, where they resolve through the *source* `search_path` - which does not contain the target schema. `get_create_index_sql()` and `get_create_table_sql()` now rewrite references to migrated collations to `COLLATE "<target_schema>"."<collation>"`, keep built-in collations (`C`, `POSIX`, `en_US.utf8`) untouched, and drop a reference to a collation which exists neither among the migrated ones nor in the target database (with a warning) instead of failing the whole object.
  - Fix - PostgreSQL Connector: Column collations were lost completely - `fetch_table_columns()` did not read `collation_schema` / `collation_name` at all, so a column declared as `name text COLLATE german_phonebook` was created with the default collation. The collation is now read, carried through `planner.convert_table_columns()` and emitted by `get_create_table_sql()`.
  - Fix - PostgreSQL Connector: A collation in a functional index expression was silently removed (`lower(name) COLLATE natural_numeric` became `lower(name)`), and the MySQL charset introducer cleanup (`_utf8'text'`) corrupted PostgreSQL quoted identifiers containing an underscore (`"natural_numeric"` became `"natural"`). Both substitutions are now applied only to non-PostgreSQL sources, while PostgreSQL expressions keep their collation, remapped to the target schema.
  - Fix - PostgreSQL Connector: A qualified or dotted collation name in an index (`COLLATE "en_US.utf8"`) was split on every dot regardless of the quoting and re-emitted as `"en_US"."utf8"`, and an operator class behind a `COLLATE` clause was swallowed. Identifier parsing now respects double quotes (new helpers `split_leading_identifier()` and `parse_identifier_parts()`).

- 2026.08.05

  - Fix - PostgreSQL Connector: Resolved multiple errors during PostgreSQL-to-PostgreSQL schema and data migration:
    - **UDT & Domain Execution Ordering**: Updated `orchestrator.py` (`run()`) and `planner.py` (`create_plan()`) to execute domain creation (`run_create_domains`) BEFORE user-defined type creation (`run_create_user_defined_types`), ensuring composite types depending on domains (such as `money_amount` referencing domain `iso_currency`) find their dependent types created on the target database. Added topological dependency sorting for composite types in `postgresql_connector.fetch_user_defined_types()` using attribute type OIDs (`attr_type_oids`).
    - **Range Type DDL Syntax**: Fixed `fetch_user_defined_types()` in `postgresql_connector.py` to emit `SUBTYPE_DIFF = ...` instead of `SUBDIFF = ...` for range types (`CREATE TYPE ... AS RANGE`), fixing syntax errors when migrating range types (such as `weight_range`).
    - **Domain `NOT NULL` Deduplication**: Updated `get_create_domain_sql()` in `postgresql_connector.py` to verify whether `source_domain_check_sql` already contains `NOT NULL` before appending `NOT NULL`, preventing invalid `NOT NULL NOT NULL` DDL syntax errors when creating domains (such as `non_empty_text`).
    - **`insert_batch` Column Alignment & JSON/JSONB Serialization**: Fixed `insert_batch()` in `postgresql_connector.py` to align payload dictionary keys directly with `insert_columns` ordering 1-to-1, and added automatic JSON serialization (`json.dumps()`) for Python objects (`dict`, `list`, `bool`, `int`, `float`), JSON `null` (`None` → `'null'`), and raw strings (such as `'corporate'` → `'"corporate"'`) destined for `json` and `jsonb` target columns (like `app_settings.value`), resolving `can't adapt type 'dict'`, type expression errors, and NOT NULL violations for JSON null.
    - **Sequence Introspection & Migration**: Implemented full `fetch_sequences()` in `postgresql_connector.py` to query sequence catalog metadata from `pg_class` (`relkind = 'S'`) and runtime `last_value` state, enabling sequence planning (`stdwf_prepare_sequences()`) and target creation prior to table creation (`stdwf_migrate_sequences()`), resolving `relation "..._seq" does not exist` errors when tables reference sequences in column default expressions.
    - **ARRAY Column Type Resolution**: Updated `fetch_table_columns()` in `postgresql_connector.py` to query `pg_catalog.format_type(a.atttypid, a.atttypmod)`. When `data_type` is `'ARRAY'`, the exact element array type (e.g. `text[]`, `integer[]`, `varchar(50)[]`, `udt[]`) is used instead of the raw `information_schema.columns` string `'ARRAY'`, resolving `syntax error at or near "ARRAY"` during table creation.
    - **Source-Aware BIT Column Defaults & Length Modifiers**: Updated `fetch_table_columns()` and `get_create_table_sql()` in `postgresql_connector.py` to preserve length modifiers for `BIT(N)` and `VARBIT(N)` columns (such as `flags bit(8)`), preventing columns from defaulting to `BIT(1)` and causing `bit string length N does not match type bit(1)` errors. Updated `get_create_table_sql()` to check `source_db_type`: for PostgreSQL sources, `BIT` default expressions (such as `'00000000'::"bit"`) are emitted directly without appending illegal `::BOOLEAN` casts, resolving `cannot cast type bit to boolean` errors, while non-PostgreSQL source databases (MySQL, MSSQL) retain bit-to-boolean default mappings.
    - **Null Value Fallback for `NOT NULL` Columns in `insert_batch`**: Added case-insensitive key lookup and `NULL` fallback handling in `insert_batch()` for target columns with `is_nullable == 'NO'`: when source rows contain `None` for a `NOT NULL` target column (e.g. legacy NULL data in source table), it uses the column default value or type-specific fallback (`''` for text/string, `0` for numeric, `False` for boolean), preventing `null value in column "..." violates not-null constraint` errors during row migration.
    - **Single-Sequence Migration Worker Execution**: Rewrote `migrate_sequences()` in `postgresql_connector.py` to create and set parameters for the single target sequence passed in `settings` rather than executing an unconstrained schema-wide loop across parallel worker threads, resolving `duplicate key value violates unique constraint "pg_class_relname_nsp_index"` errors during parallel sequence migration.
    - **BC Dates & Infinity Timestamps String Type Casters**: Registered string type casters in `postgresql_connector.connect()` for `DATE`, `TIMESTAMP`, `TIMESTAMPTZ`, `TIME`, `TIMETZ`, and `INTERVAL` OIDs (1082, 1114, 1184, 1083, 1266, 1186), preventing `psycopg2` from attempting to instantiate Python `datetime.date` objects for BC dates (such as `0001-01-01 BC` in `type_zoo`) which caused `ValueError: year -1 is out of range`.
    - **Index `COLLATE` Clause & Operator Class Formatting**: Updated `get_create_index_sql()` in `postgresql_connector.py` to parse `COLLATE`, operator class (e.g. `event_type gin_trgm_ops`), and `NULLS FIRST`/`LAST` clauses separately from column names, emitting `"event_type" "gin_trgm_ops"` and `"name" COLLATE "natural_numeric"` instead of wrapping the clauses inside column quotes (such as `"event_type gin_trgm_ops"`), resolving `column "... gin_trgm_ops" does not exist` and `column "... COLLATE ..." does not exist` errors when creating custom indexes.
    - **Index Access Method (`USING gin`, `USING gist`) Preservation**: Updated `fetch_indexes()` and `get_create_index_sql()` in `postgresql_connector.py` to extract and preserve `USING` access method clauses (`USING gin`, `USING gist`, `USING hash`, `USING brin`, `USING spgist`), preventing non-btree indexes (such as `customer_notes_body_gin_idx` on `tsvector` columns) from defaulting to btree and raising `index row size ... exceeds btree version 4 maximum ...`.

- 2026.08.04

  - Feature - SQLite Connector: Added `ddl` connectivity, so a SQLite migration can start from SQL script files (a `sqlite3 db .schema` / `.dump` output or hand-maintained scripts) instead of a database file, with the data coming from CSV files configured under `data_export`. This also resolves the migration failing with `'SQLiteConnector' object has no attribute 'parse_ddl_files'` - the connector supported only `native` connectivity, while with `connectivity: "ddl"` the planner skips both the connection check and the pre-migration analysis and calls `parse_ddl_files()` directly.
    - `ddl: path:` accepts a directory, a file mask or one specific file (relative paths are resolved against the directory of the config file), matching the other DDL based connectors.
    - Instead of a hand-written DDL parser, `parse_ddl_files` replays the scripts into a **staging SQLite database** which is then introspected by exactly the same code as a native connection - SQLite is the only parser that fully understands its own DDL, so CHECK constraints, generated columns, `AUTOINCREMENT`, functional and partial indexes, views and triggers are all recognized without a second implementation to maintain.
    - The staging database path is derived from the list of script files, so the planner and every orchestrator worker resolve it to the same file; it is written under a temporary name and moved into place atomically, and any worker rebuilds it if it is missing. It is placed in `data_export.conversion_path` when configured, otherwise in the system temp directory, and its location is logged.
    - The scripts are first executed in one go; when that fails they are replayed statement by statement (using `sqlite3.complete_statement`, which knows about string literals and about the `BEGIN ... END` body of a trigger), so a single bad statement no longer costs every object in the file. Skipped statements are counted and the summary is logged at INFO - `WARNING` ranks as more verbose than `INFO` in this tool, so a warning-only report would have been invisible at the default log level - while each individual statement is logged at WARNING.
    - If the scripts contain `INSERT` statements (a full dump) the data lands in the staging database and is migrated from there, so no `data_export` block is needed; a configured CSV data source still takes precedence, as for the other DDL based connectors.
    - Scripts are read as UTF-8 with a fallback to latin-1, and an unsupported `connectivity` value, a missing `ddl: path:` block, a path matching no file and scripts producing no objects at all are each rejected with their own explanatory message at start-up. `config_parser.get_connect_string` handles both SQLite modes and treats a missing, empty or differently cased `connectivity` as `native`.
  - Feature - SQLite Connector: Added new source database connector `sqlite` (`credativ_pg_migrator/connectors/sqlite_connector.py`, registered in `MigratorConstants.get_modules()`), modelled on the PostgreSQL connector. It uses the `sqlite3` module of the Python standard library, so SQLite is the only source engine which needs no driver installation. The source section consists of `type: "sqlite"` and `database` holding the path to the database file (relative paths are resolved against the directory of the config file) - `host`, `port`, `username` and `password` are not used, and `schema` must be `main` or the name of an attached database, because SQLite has no schemas. The file is opened read-only whenever possible and falls back to read-write with a warning when a hot journal or WAL has to be recovered first.
    - Two properties of SQLite required a different approach than the other connectors. SQLite has no data dictionary for a part of its metadata, so the connector carries a quote and parenthesis aware DDL parser reading CHECK constraints, generated column expressions, the `AUTOINCREMENT` marker, the expressions of a functional index and the `WHERE` of a partial index back out of the `CREATE` statements stored in `sqlite_master` - none of which any `PRAGMA` exposes. And SQLite is dynamically typed, so the declared type of a column selects the PostgreSQL type while the values themselves are coerced to what the target column expects during the data migration.
    - Migrated: tables and data, primary keys (always taken from the column metadata, because SQLite creates no index for an `INTEGER PRIMARY KEY` on a rowid table - composite keys and `WITHOUT ROWID` tables included), secondary and `UNIQUE` indexes including functional ones, foreign keys with their `ON DELETE` / `ON UPDATE` rules (a short `REFERENCES parent` without a column list is resolved against the parent primary key), CHECK constraints, generated columns (`STORED` and `VIRTUAL`, both migrated as `STORED` and excluded from the `INSERT`), default values, views and triggers.
    - Identity columns: an `INTEGER PRIMARY KEY` (the rowid alias) and `AUTOINCREMENT` columns become PostgreSQL identity columns. The rowid alias is recognized by the rule SQLite itself applies - declared type exactly `INTEGER`, single column primary key, rowid table - so a column declared `INT` or a key of a `WITHOUT ROWID` table is correctly not treated as one. The next value is read from `sqlite_sequence` when available, otherwise derived from the data.
    - Data types: the mapping covers the type names of the dialects SQLite databases are commonly created from, not only its five storage classes. `INTEGER` maps to `BIGINT` (a SQLite `INTEGER` holds up to 8 bytes), `INT` to `INTEGER`, `BLOB` to `BYTEA`, `REAL` / `FLOAT` / `DOUBLE` to `DOUBLE PRECISION`, and a column declared with no type at all to `TEXT`.
    - Value conversion on insert, driven by the target column type: `0`/`1` and text forms to `BOOLEAN`, an `INTEGER` in a date column interpreted as a Unix timestamp and a `REAL` as a Julian day number, `BLOB` passed through for `BYTEA` and decoded for text targets, and non-string storage classes stringified for text targets. TEXT values which are not valid UTF-8 are decoded with replacement instead of aborting the batch.
    - Views and triggers are translated with `sqlglot` (`read='sqlite'`) plus a SQLite specific function mapping. A trigger becomes a PL/pgSQL trigger function plus a `CREATE TRIGGER`, preserving timing, event, `UPDATE OF` and `WHEN`, converting `SELECT RAISE(ABORT, ...)` to `RAISE EXCEPTION` and appending the `RETURN` matching the trigger kind; the function carries `SET search_path` so the unqualified names of a SQLite trigger body resolve in the migrated schema. In views the names of migrated tables and views are qualified with the target schema for the same reason.
    - Virtual tables (FTS, RTREE) and their shadow tables are skipped with a warning, as are the hidden columns of a virtual table. Partial indexes are migrated without their `WHERE` condition and a partial `UNIQUE` index is degraded to a non unique index (keeping it unique would reject rows SQLite accepted) - both are warned about and the original condition is recorded in the index comment. Constraint names which SQLite does not provide itself are generated, reduced to plain characters and shortened so they survive PostgreSQL's 63 byte identifier limit without colliding.
    - Pre-migration analysis is implemented for all five metrics; row counts are real `count(*)` queries because SQLite keeps no row estimates, and table sizes are only available when the library was compiled with `SQLITE_ENABLE_DBSTAT_VTAB`. Post-migration validation (row counts, table checksums, random row sampling, LOB sizes) is supported.
    - SQLite has no stored functions or procedures, no sequences, no user defined types, no domains and no comments - those steps are no-ops.

    - `schemas`: a schema named after the package is created (`CREATE SCHEMA IF NOT EXISTS`) and the routines keep their own names inside it (`PKG_AUDIT.LOG_CHANGE` → `pkg_audit.log_change`), which preserves the `package.routine` call syntax.

    Every call into a package is rewritten to the chosen layout wherever this connector generates PL/pgSQL (functions, procedures and triggers), including unqualified calls between routines of the same package, and a call that forms a whole statement gets the `PERFORM` that PL/pgSQL requires — previously such a call was emitted as `pkg_audit.log_change(...);`, which is not valid PL/pgSQL and made every calling routine fail to create. The final object-validity pass accepts a package as valid when at least one of its functions exists, in either layout.
    - Limitations: the split is best-effort like the rest of the PL/SQL conversion. **Package state** (package level variables, constants and cursors) has no PostgreSQL equivalent and is not migrated - it is reported with a warning. Overloaded package routines collapse onto the same target name (PostgreSQL overloads by argument types, so this works only when the signatures differ). Routines whose block structure cannot be followed are skipped with a warning, and Oracle-specific functions inside the bodies are still subject to the usual best-effort translation.
  - Fix - Oracle Connector: References to the source schema inside a converted function/procedure are re-pointed to the target schema also in their unquoted form (`MIGTEST.audit_log`, as found in `ALL_SOURCE`), not only in the quoted form `DBMS_METADATA` emits. Package routines created in a package schema keep pointing at the migration target schema for tables.

The first check covers generated columns: `GENERATED ALWAYS AS (...) STORED` requires PostgreSQL 12 or newer, so a source schema containing computed/virtual columns cannot be migrated to an older target. The previous approach re-quoted identifiers that were already quoted (`"CREDIT_LIMIT"` became `""CREDIT_LIMIT""`), ignored the configured name-case handling (so the expression referenced `"CREDIT_LIMIT"` while the target column is `"credit_limit"`), rewrote column names and `+` operators inside string literals, and never parenthesized the result although `GENERATED ALWAYS AS (...) STORED` requires it. Shared by all source connectors that report generated columns (Oracle, MySQL/MariaDB, Sybase ASE).
  - Fix - PostgreSQL Connector: Prevented niladic SQL keyword-functions from being emitted as quoted string literals in `CREATE TABLE` column defaults (e.g. an Oracle `DEFAULT USER` became the constant text `'USER'`). For string columns the default was only left unquoted when it contained `||`, `(`, `)` or `::`; the parenthesis-less keywords (`current_user`, `current_role`, `session_user`, `user`, `current_catalog`, `current_schema`, `current_timestamp`, `current_date`, `current_time`, `localtime`, `localtimestamp`) are now recognized as expressions as well, while genuine string literals are still quoted. Same fix as on the 0.15 maintenance branch, which is not yet merged here.
  - Fix - Oracle Connector: System-managed pseudo-tables are no longer listed for migration. `fetch_table_names` now also excludes index-organized table overflow / mapping segments (`IOT_TYPE` `IOT_OVERFLOW` / `IOT_MAPPING`, named `SYS_IOT_OVER_<id>`) and recycle-bin tables (`DROPPED='YES'`, named `BIN$...`).
